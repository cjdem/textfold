# 本机详细日志

写到 `notes/YYYY-MM-DD-<slug>.md`，中文，**不提交**（`notes/` 已被 gitignore）。

提交版是给别人的记录，这一份是给你自己的思考。写得有多细都不算细 —— 六个月后你会想知道当时为什么排除了那条路、哪个数字是在什么条件下测的、哪里你其实没底。

从真实 diff 和真实命令输出写，不要凭记忆。记不清的地方就写「记不清」，不要补一个像样的理由。

---

```markdown
# <一句话说清这次优化>

**日期：** YYYY-MM-DD
**分支：** `<分支名>`（已合并 / 已放弃）
**耗时：** 大约 <多久>

## 为什么做这个

起因是什么，原来的做法哪里不舒服。如果有具体的触发场景或数据，写下来 —— 「感觉慢」和「2512.23916 在第 3 层要等 4 秒」是完全不同的两件事。

## 目标与验收标准

当初说好的「更好」指什么，怎么算做到了。如果中途改过，记下改成了什么、为什么。

## 勘察到的地形

- 涉及的模块和函数（`文件:行`），数据是怎么流的
- 一开始不知道、后来才发现的约束
- 另外几个候选方案，以及为什么没选它们

## 实际做了什么

改动的清单，每条一行，附上关键处的位置。带上那些最终没进提交、但你确实写过的代码 —— 走过的死路也是信息。

## 验证结果

真实命令和真实输出。**没测的东西要写清楚没测**：

- 缩放流畅度：<windows 上测不了 / 测了，数字是 …>
- 测试：<85 个用例，全绿>
- 其他：<…>

## 数字

| 指标 | 改动前 | 改动后 | 怎么测的 |
|---|---|---|---|
| | | | |

## 走过的死路

试过但不行的做法，各写清楚卡在哪里。这一节往往比结论有用 —— 下次你会先跳到这儿。

## 没底的地方

哪里你不确定，哪个决定是权宜的，什么情况下这套改动会出问题。不要因为「反正合了」就不写。

## 下次可以继续

这次没做但值得做的，或者需要重做的前提。
```

---

这份日志跟着分支走，不跟着提交走。分支被放弃时它同样要写 —— 放弃的原因尤其值得写。
