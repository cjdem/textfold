## 结论

129 个提交里，大部分是 Pi / WorkBuddy / Claude Code / Codex 这些 agent runtime 的改动，或者是 Electron、站点、PyPI、release note 和插件；这些对本 fork 要么不适用，要么已经被“API-only + Magpie”取代，**skip**。

真正值得看的有三类：

1. **正确性/安全/Windows 编码**：Host 校验、UTF-8 文本读写、旧 GBK 数据迁移、模型回复的多种 JSON 形状、只支持流式的服务、`TEXTFOLD_NO_MODELS`、EPUB 编码。
2. **中文/CJK 阅读**：中文句子切分、五级折叠、CJK 规则只作用于中日文文档。
3. **读者功能/本地处理**：Aa 菜单与缩放沙箱、整篇 Markdown 保存、多文件导入、批量删除/恢复、主题、侧栏固定、可选的嵌套文件夹；MinerU 端点配置是 fork-specific，不属于上游。外部联动、阅读语言 API、订阅/agent 聚合、ChatGPT 本地桥、Markdown 原地重折暂不做。

## MinerU API：多文件与自部署端点

### 当前实现

- [`engine.py:37`](textfold/engine.py:37) 把 `API` 硬编码为 `https://mineru.net/api/v4`；[`engine.py:62`](textfold/engine.py:62) 只读 `mineru_api_key`。
- [`engine.py:186`](textfold/engine.py:186) 的 `_api_read` 每次 `POST /file-urls/batch` 只放一个文件，`PUT` 到返回的签名 URL；[`engine.py:161`](textfold/engine.py:161) 轮询 `GET /extract-results/batch/{batch_id}`，最后下载 zip。
- [`pdf.py:16`](textfold/pdf.py:16) 的上传上限是 100 MiB，比云 API 的 200 MB 更严。

### 云 API 要求（v4）

- 单文件 ≤ 200 MB，≤ 600 页；batch ≤ 200 个文件；300 次提交/分钟；10,000 文件/天（HTML 最多 100）；结果查询 1,000 次/分钟；每天 2,000 页优先，超出后降优先级。
- 官方文档列出的格式是 PDF、图片（png/jpg/jpeg/jp2/webp/gif/bmp）、Doc/Docx/Ppt/Pptx；当前代码还列了 xls/xlsx/html，使用时以实际 API 返回为准。
- 参考：[MinerU API 文档](https://mineru.net/doc/docs/index_en/)、[限流](https://mineru.net/doc/docs/limit_en/)。

### 自部署（V1）

- 用 `mineru-kit api-server --host 127.0.0.1 --port 8000 --tier standard` 启动；接口是 `/v1/file_parse`（同步，默认等 300 秒，`wait_timeout` 1–3600）和 `/v1/tasks`（异步），不是云端的 `/api/v4/file-urls/batch`。
- 限制：200 MiB/文件，100 文件/任务；ZIP 输出需要 `response_format=zip` / `output_formats=zip`；batch ZIP 是编号目录 + status manifest；本地可无 key。
- 参考：[MinerU V1 HTTP API](https://opendatalab.github.io/MinerU/usage/http_api/)、[示例脚本](https://github.com/opendatalab/MinerU/blob/master/scripts/http_api_example.sh)。

### 多文件：逐文件队列，不用 batch

- 推荐的实现：浏览器一次拿到多个 `File`，逐个调用现有 `/api/files`；每个文件仍生成一个 `Jobs.convert` job，转换队列保持一次一个；侧栏逐个显示，toast 汇总成功/失败/等待。每文件的进度、停止、重试都不变。
- 不使用 MinerU 的 200 文件 batch：batch 会把多文件绑在同一个请求/批次上，部分失败、按文件名映射、停止和重试都更复杂；而本 fork 的转换队列本来就是串行，batch 没有实际收益。300 次/分钟和 10,000 文件/天的限制对个人批量也远未触及。
- 建议每次拖入最多 50 个文件，重复文件按现有 pid 规则跳过；当前 100 MiB 上限先保留（提高到 200 MB 是另一个改动）；600 页上限和每天 2,000 页优先额度在错误/提示里说明。

### URL / 自部署配置

- 值得做：加 `mineru_api_url` 设置，默认 `https://mineru.net/api/v4`；校验 `http(s)://`、去掉末尾 `/`；`engine.status()` 报告当前 base；`_api` 用它拼接；设置页放在 MinerU 区域，提供“恢复官方地址”。
- 但**只改 URL 不能支持 `mineru-kit` 自部署**：自部署是 V1 的 `/v1/file_parse`/`/v1/tasks`，请求、轮询和输出 zip 的结构都不同，需要单独的 V1 adapter（multipart 上传、任务轮询、把输出映射到现有 `structured_content.json`）。当前 `_put` 用的是 `HTTPSConnection`，自部署若是 `http://` 也要在 adapter 里处理。建议拆成两次：
  1. 可配置 v4 base URL（小；支持官方或 v4 兼容代理）。
  2. self-hosted V1 adapter + `mineru_api_mode`（`cloud` / `self-hosted`，默认 cloud；本地 key 可选）。这次不要假装 URL 一项就覆盖自部署。
- 安全：只把 key 发到配置的 base；签名上传 URL 可能是别的主机，当前的 `_put` 不带 key，保持这个行为；self-hosted 也按同源规则处理。
