# TextFold 0.11.0 is prepared for its tag

**Date:** 2026-10-24
**Branch:** `worktree-release-0.11.0`

## What and why

The release workflow existed, but a tag build published the placeholder body "Building the app.", and it never ran
the Python suite. The fork's first release since v0.10.7 needs one version in the code, the app and the site, release
notes the tag build publishes, and the suite as a gate. This prepares 0.11.0; nothing is tagged or pushed here.

## The change

- `.github/workflows/desktop.yml` — the draft's body is `docs/releases/<tag>.md`; a tag build stops before the draft
  without that file, and it edits the draft's notes on a rerun; after the payload is prepared it runs the Python suite
  with `PYTHONUTF8=1` (a clean en-US runner's ANSI page cannot encode the suite's text).
- `tests/test_release.py` — new: the draft's notes file and its edit on a rerun, the notes check before the draft, the
  Python step's UTF-8 mode, and the current version's notes file; a step's comments are stripped before it is checked,
  so a comment cannot satisfy a check of what the step runs.
- `textfold/__init__.py`, `desktop-mygo/mygo.json`, `site/strings.py` — 0.10.7 to 0.11.0.
- `docs/releases/v0.11.0.md` — new: the release notes, English and a Chinese summary.
- `README.md` / `README.zh-CN.md` — the 0.11.0 entries: the resume, cross-process saves, and the reader/library round.
- `docs/DEVELOPMENT.md` — a Releases section: the three version strings, the notes file, the tag and push order, what
  the tag build does.
- `desktop-mygo/README.md` — where the release notes come from.

## Decisions

- 0.11.0, not 0.10.23: this clone also holds upstream's `v0.10.8`–`v0.10.22`, and 0.11.0 keeps the fork's release line
  out of that namespace.
- The notes are a tracked file, not the tag annotation or a manual edit after publishing: the workflow publishes the
  draft itself, so the body must be right before the build.
- The tag build runs the Python suite with the payload's own Python, after the payload is prepared: no extra install,
  and the tests run against the repository's code.
- The push order stays the human's: `main`, then `v0.11.0` alone; `git push --tags` is refused in the docs because the
  upstream tags would start a failing workflow for each.

## Concurrency and locks

None: this changes version strings, documentation and CI, and writes no persisted application data.

## How it was verified

- `python .claude/hooks/verify.py` — 530 tests, OK (527 before; 3 added).
- `go -C desktop-mygo test ./...` — the version equality and the other Go tests stay green.
- `git diff --check` — clean.
- The independent verifier read the workflow, the tests, the notes and the docs. Its first read found: the CI Python
  step needed UTF-8 mode on a clean en-US runner (the suite's locale test); the Zotero and "submitted anew" wording
  claimed more than the code does; the record called smoothness unaffected; the record claimed a verification not yet
  run; the release test was too weak; and the docs-checked list omitted the process documents. All were fixed above. A
  second read confirmed them and found one remaining bypass in the release test: an inline YAML comment could satisfy
  its string checks. The test now strips comments from a step before checking it; its notes are in the local log.

## Not measured

- The tag workflow itself was not run: this worktree creates no tag and does not push. The YAML and the steps were read
  and the version checks were run locally; the first real run is the release.
- No reader or rendering code changed; smoothness was not measured (`tools/zoombench.py` still needs `playwright` and
  exported comparison pages, neither is here).

## Pitfalls

- A rerun reuses a draft left by a failed build; the workflow now edits its notes from the file every time.
- The notes file must be in the tagged commit, not added in a later commit on `main`; the tag build checks out the tag.
- The payload Python runs the suite from the repository root; it imports the repository's `textfold/`, not the copy
  under `payload/app`.
- `v0.10.8`–`v0.10.22` are upstream tags in this clone; pushing all tags would start the desktop workflow for each.
- `zotero.apply` (a Zotero item read into a stored document's meta) writes `meta.json` without the papers lock; a
  re-conversion can interleave with it. The release note claims the Zotero index, not every Zotero route; this gap
  predates this change and is not fixed here.

## Rejected

- A new release workflow: `desktop.yml` already builds, signs and publishes; only the notes and the suite gate were
  missing.
- Release notes in the tag annotation (`--notes-from-tag`): harder to review than a tracked file.
- Publishing the placeholder and editing the release afterwards: the release body is what the update toast opens, and
  it should be right when it goes live.
